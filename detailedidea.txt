# MASTER DEVELOPMENT PROMPT
# V-DJ — Autonomous Hybrid AI DJ & Multi-Phone Stereo Party Platform

## 1. ROLE AND MISSION

Act as a senior full-stack software architect, Laravel engineer, React/TypeScript engineer, professional DJ audio-systems engineer, Web Audio API specialist, WebRTC engineer, and AI integration specialist.

Your mission is to design, build, test, and deliver **V-DJ**, a production-minded, mobile-first Progressive Web Application (PWA) that functions as an autonomous AI DJ.

V-DJ should allow users to describe the music experience they want in natural language, select available music sources, and let an AI DJ automatically:

1. Discover and select suitable music.
2. Organize tracks into an intelligent DJ set.
3. Create a natural energy progression.
4. Analyze BPM and musical beat positions.
5. Prepare the next track while the current track plays.
6. Synchronize tempos and musical downbeats.
7. Perform automatic DJ transitions.
8. Apply EQ adjustments and audio effects.
9. Maintain uninterrupted playback.
10. Broadcast the mixed music to multiple phones connected to the same party room.
11. Distribute left and right stereo channels across separate phones.
12. Allow users to override the AI DJ and control the experience manually.

The final product must be a genuinely functional DJ application, not a UI demonstration, static prototype, or collection of disconnected components.

### Core product vision

A user should be able to open V-DJ, enter:

"Start with relaxing lo-fi music, gradually build into energetic melodic house around 126 BPM, introduce powerful progressive tracks, and finish with uplifting electronic music."

The application should understand this request, generate a suitable music sequence, and operate as an autonomous DJ.

The user should not need to manually manage every track or transition.

The application should also allow friends to connect their phones to one party room, turning multiple smartphones into a coordinated stereo speaker system.

**The ultimate experience: One AI DJ, multiple phones, one synchronized party.**

# 2. NON-NEGOTIABLE ARCHITECTURAL PRINCIPLES

## 2.1 Separation of Brain and Muscle

Maintain strict separation between backend intelligence and client-side audio execution.

**Laravel is the Brain.**

Laravel handles:

- Authentication and authorization.
- User preferences.
- Party room management.
- Music metadata discovery.
- External music provider integrations.
- AI setlist generation.
- Transition planning.
- Session management.
- WebSocket communication.
- WebRTC signaling.
- Peer registration.
- Party state synchronization.

**React and TypeScript are the Muscle.**

The browser handles:

- Audio playback.
- Audio decoding.
- BPM analysis.
- Beat and downbeat detection.
- Tempo synchronization.
- Audio mixing.
- EQ.
- Audio effects.
- Crossfading.
- Transition scheduling.
- Stereo channel separation.
- Local audio processing.
- WebRTC audio transmission.
- Guest audio playback.

**Critical restriction:**

NEVER transmit raw music audio through PHP, Laravel controllers, Laravel queues, or Reverb.

The audio must remain on the client devices and travel directly between devices through WebRTC.

Laravel must only coordinate the application and its connections.

## 2.2 Reliability over artificial completeness

Never mark a feature as complete simply because:

- Its button exists.
- Its component renders.
- An API endpoint returns HTTP 200.
- A WebRTC connection reports connected.
- A transition animation plays.
- A track appears in the queue.

A feature is complete only when its actual intended functionality works.

Never implement fake BPM values, simulated audio synchronization, artificial playback progress, placeholder stream URLs, or mocked transitions in production code.

If an external service requires API credentials, approval, or unavailable permissions, implement the integration correctly, expose its actual status, and document what remains dependent on external access.

Do not silently replace unavailable functionality with fabricated success.

## 2.3 Incremental development

Do not attempt to generate the entire application in one enormous implementation step.

Build the application in defined phases.

For each phase:

1. Inspect the existing codebase.
2. Understand the architecture.
3. Identify dependencies.
4. Implement the required functionality.
5. Run relevant automated tests.
6. Fix discovered issues.
7. Verify actual behavior.
8. Document completed work.
9. Proceed only when the phase's acceptance criteria are satisfied.

Never discard working code or rewrite stable modules unnecessarily.

Preserve existing functionality when introducing new features.

# 6. HYBRID DUAL-BRAIN AI DJ

Create:

`App\Services\AI\AiDjPlannerService`

Use a strategy-based architecture with two planning engines.

Both engines must return the exact same validated output structure.

## 6.1 Gemini Cloud Brain

Implement:

`GeminiPlannerStrategy`

Responsibilities:

1. Accept the user's natural-language music request.
2. Analyze the requested musical atmosphere.
3. Understand genre preferences.
4. Determine the intended energy progression.
5. Evaluate available tracks.
6. Consider BPM compatibility.
7. Consider known musical key information when available.
8. Select a coherent track order.
9. Assign transition styles.
10. Produce a structured DJ setlist.

Use Gemini structured output capabilities with a strict JSON schema.

Make the model configurable through environment variables.

Default configuration:

```env
AI_DJ_DEFAULT_MODE=gemini
GEMINI_API_KEY=
GEMINI_MODEL=
```

Do not hardcode an outdated model identifier.

The planner must validate every model response before returning it.

Reject:

- Invalid JSON.
- Missing required fields.
- Unknown track IDs.
- Invalid transition styles.
- Invalid BPM values.
- Out-of-range energy values.
- Impossible transition timings.

The AI must only select tracks that exist in the supplied available-track list.

It must never invent tracks, artists, IDs, or stream URLs.

### AI planning logic

The AI should consider:

- Genre compatibility.
- Energy progression.
- BPM compatibility.
- Musical key compatibility when metadata is available.
- Track duration.
- Track quality and availability.
- Transition feasibility.
- The user's requested beginning, middle, and ending.

Do not force every set to have the same energy curve.

The user should receive a music experience that reflects the actual prompt.

## 6.2 Local Deterministic Brain

Implement:

`LocalPlannerStrategy`

This engine must work without external AI API calls.

Responsibilities:

- Keyword matching.
- Genre matching.
- BPM sorting.
- Energy scoring.
- Track ranking.
- Transition assignment.
- Smooth progression planning.

Use deterministic rules.

Suggested BPM-based transition selection:

| BPM difference | Transition |
|---|---|
| 0–7 BPM | 16-bar bass swap |
| 8–14 BPM | 8-bar filter sweep |
| Above 14 BPM | 4-bar echo out |

The engine should also account for genre compatibility and track energy.

It must not claim that it understands natural-language requests as intelligently as Gemini. Its actual capabilities should be clearly represented.

## 6.3 Automatic fallback

When Gemini:

- Is not configured.
- Returns HTTP 429.
- Times out.
- Returns invalid structured output.
- Encounters a temporary service error.

Automatically attempt the local planner.

Do not expose unnecessary internal API errors to the user.

Record which engine actually generated the setlist.

Use a configurable timeout, retry policy, and one-hour cache for identical normalized prompt and tracklist combinations.

Never cache user-specific credentials or sensitive information with planning results.

## 6.4 Standardized output schema

Both planners must return this contract:

```json
{
  "engine_used": "gemini",
  "vibe_summary": "A gradual journey from relaxing music to energetic melodic house.",
  "setlist": [
    {
      "order": 1,
      "track_id": "track_001",
      "title": "Track Title",
      "artist": "Artist Name",
      "source_type": "audius",
      "estimated_bpm": 124,

        "style": "bass_swap",
        "duration_bars": 16,

          "lowshelf_cut",
          "highpass_sweep",
          "reverb_tail"
        ]
      }
    }
  ]
}
```

Important:

The actual stream URL must come from the relevant music-source adapter.

Do not trust an AI-generated stream URL.

Resolve and validate playable sources independently before starting playback.

Extend the schema with musical key, detected BPM, source metadata, and transition confidence where useful, while preserving the core contract.

# 8. PROFESSIONAL DUAL-DECK DJ AUDIO ENGINE

`frontend/src/audio/DjAudioEngine.ts`

React must not control individual audio-processing operations through repeated component renders.

Use dedicated audio classes and predictable lifecycle management.

## 8.1 Dual-deck architecture

Implement:

- Deck A.
- Deck B.
- Shared master output.
- Shared effects bus.
- Master limiter.
- Independent deck controls.

Each deck must contain:

1. Audio playback source.
2. Channel gain.
3. Three-band EQ.
4. High-pass/low-pass filter.
5. Effects send.
6. Analyser.
7. Playback state.
8. BPM information.
9. Beat offset.
10. Transition state.

Suggested EQ configuration:

| Band | Filter |
|---|---|
| Low | Lowshelf at 250 Hz |
| Mid | Peaking at 1 kHz |
| High | Highshelf at 4 kHz |

Support smooth parameter automation.

Avoid abrupt gain changes that create clicks or audio artifacts.

## 8.2 Audio source compatibility

Support both local decoded audio and remote media streams.

Use:

- AudioBufferSourceNode for suitable decoded local tracks.
- MediaElementAudioSourceNode for streaming media.

Check CORS compatibility before routing remote audio through Web Audio.

If a provider's streaming configuration prevents analysis or audio routing, report the limitation and use an authorized compatible playback strategy.

Do not assume every remote stream can be analyzed through an AnalyserNode.

## 8.3 Beat and downbeat detection

Implement:

`TrackAnalysisService`

When a track is loaded into a standby deck:

1. Analyze its audio.
2. Estimate BPM.
3. Detect the first reliable beat.
4. Determine the downbeat offset.
5. Calculate beat duration.
6. Calculate bar duration.
7. Store analysis results.

Use:

`web-audio-beat-detector`

or a maintained compatible library.

Provide confidence values.

Do not assume the BPM detector always returns a correct result.

If analysis confidence is low, allow manual BPM adjustment.

Support half-time and double-time BPM ambiguity.

## 8.4 Beatmatching

Implement actual tempo synchronization.

Calculate the required playback-rate adjustment using the active and standby BPM.

For example:

If Deck A is playing at 120 BPM and Deck B is 126 BPM, calculate an appropriate tempo adjustment before mixing.

Align downbeats using the detected beat offsets.

Gradually adjust tempo rather than introducing sudden changes.

Important:

A basic playbackRate adjustment also changes pitch. Either implement pitch-preserving time stretching or clearly expose the pitch behavior and limitations.

Do not claim professional pitch-locked beatmatching unless it is genuinely implemented and tested.

## 8.5 Transition Scheduler

Create:

`TransitionScheduler.ts`

Requirements:

- Use AudioContext.currentTime.
- Implement a lookahead scheduler.
- Use approximately 25 ms scheduling intervals.
- Maintain approximately 100 ms scheduling lookahead.
- Schedule important audio changes against musical timing.
- Avoid relying on JavaScript setInterval for sample-accurate execution.

Calculate:

```text
Beat duration = 60 / BPM

Bar duration = 4 × Beat duration
```

Schedule transitions at appropriate bar boundaries.

Handle:

- Pausing.
- Resuming.
- Seeking.
- Track loading delays.
- BPM changes.
- Interrupted playback.
- Manual transition triggers.

Cancel obsolete scheduled operations when the playback state changes.

## 8.6 Transition types

Implement four real transition algorithms.

### A. Bass Swap

1. Prepare the incoming deck.
2. Match its tempo.
3. Start it at the correct beat boundary.
4. Gradually increase its gain.
5. Reduce its bass EQ.
6. Perform the bass exchange at a synchronized downbeat.
7. Fade the outgoing deck.
8. Complete the handoff.

Use safe audio parameter scheduling to avoid clicks.

### B. Filter Sweep

1. Start the incoming track.
2. Introduce its audio gradually.
3. Raise the outgoing deck's high-pass cutoff.
4. Automate the filter smoothly.
5. Reduce the outgoing deck's gain.
6. Complete the transition.

### C. Echo Out

1. Increase the outgoing deck's effects send.
2. Apply tempo-synchronized delay.
3. Reduce the dry signal.
4. Allow the delay tail to decay.
5. Bring the incoming deck forward.

Suggested dotted-eighth delay:

```text
Delay = (60 / BPM) × 0.75
```

### D. Slam Cut

Schedule an instantaneous crossfader change on a selected musical downbeat.

Do not trigger arbitrary cuts between beats unless the user explicitly requests an immediate manual cut.

## 8.7 Effects bus

Create a shared effects bus with:

- Delay.
- Feedback control.
- Procedural convolution reverb.
- Effects send levels.

Ensure feedback is safely limited.

Prevent runaway audio levels and excessive clipping.

## 8.8 Master output

Route:

Deck A + Deck B → Master Gain → Dynamics Compressor → Output Distribution.

Provide two outputs:

1. Local speakers.
2. MediaStreamAudioDestinationNode for WebRTC broadcasting.

Allow the host to mute local speakers while continuing to transmit the master mix to guests.

Include master volume and clipping protection.

# 10. ADVANCED AUDIO SYNCHRONIZATION

This is one of the most important engineering requirements.

Multiple phones must reproduce the same music as closely together as browser and device limitations permit.

A WebRTC connection alone does not guarantee synchronized speaker output.

Implement an actual synchronization strategy.

## 10.1 Clock synchronization

Exchange clock information over:

`RTCDataChannel("sync-clock")`

The host periodically sends:

- Host audio clock.
- Host monotonic clock.
- Session playback position.
- Playback state.

Guests respond with timestamps.

Use an NTP-style ping/pong approach to estimate:

- Round-trip time.
- Clock offset.
- Clock drift.
- Network jitter.

Do not simply assume that RTT divided by two is the complete one-way audio latency.

Use repeated samples and a stable estimation method.

## 10.2 Drift correction

Implement gradual guest playback synchronization.

Monitor:

- Estimated host playback position.
- Guest playback position.
- Audio buffering.
- Network jitter.
- Clock drift.

Apply small corrections where technically possible.

Avoid sudden playback jumps or audible speed fluctuations.

Separate clock synchronization from acoustic speaker alignment.

## 10.3 Manual latency adjustment

Provide a guest-side fine-tuning slider:

```text
Minimum: -150 ms
Maximum: +150 ms
Default: 0 ms
```

Allow guests to adjust synchronization while listening.

Persist the setting for the current session.

## 10.4 Important synchronization limitation

Do not promise perfect phase alignment across arbitrary smartphones.

Different devices have different:

- Audio output latency.
- Bluetooth latency.
- Speaker hardware.
- Browser audio pipelines.
- Network conditions.
- Operating-system scheduling behavior.

The implementation must measure and compensate where possible, report synchronization quality, and clearly distinguish estimated network latency from actual acoustic output latency.

Prioritize wired or low-latency audio output when testing the stereo party feature.
